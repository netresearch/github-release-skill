- On a 0.x version, `suggest-version.sh` suggests a patch bump for `feat:` commits and raises the middle number only for a breaking commit; `release-process.md` and step 2 of the release flow say to raise the middle number of a 0.x package only for a breaking change, after reading its changelog and API diff. Under 0.x the caret admits only the current middle number (`^0.54` takes 0.54.* only), so each needless middle bump requires every consumer to widen its constraint and release.
- `suggest-version.sh` asks git-cliff (`uvx git-cliff@latest --bumped-version`, or a `git-cliff` binary on PATH) for the next version, with the skill's own configuration `suggest-version.cliff.toml`, instead of parsing commit messages itself. The output keeps `current:`, `suggested:` and `bump:`; without uv and git-cliff, without that configuration, or for a range of only chore, docs, ci, test, style, build or untyped commits it reports `bump:unknown`. The inputs git-cliff answers differently from the 0.x rule (0.0.z, a subject that opens with `BREAKING CHANGE:`, squash-body bullets, pre-release tags) are listed in `release-process.md`; on 0.x the changelog BREAKING entries stay authoritative.
